## Required behavior

Expose PostgreSQL-style single-collection SELECT through REST v2
`/v2/vectordb/entities/sql_query`. Cover field and JSON-path projection, aliases,
scalar predicates and positional parameters, grouping, COUNT/SUM/AVG/MIN/MAX,
exact COUNT DISTINCT, ordering/pagination, arithmetic and temporal expressions,
and pgvector-style vector search. JSONBench Q1 through Q5 are acceptance cases,
not proof of correctness by themselves.

Reject unsupported syntax explicitly: joins, subqueries, HAVING, windows, CTEs,
set operations and writes. Do not silently discard parsed clauses. SQL NULL,
cast, integer precision, timezone and distance semantics need explicit tests.

## Implementation boundaries

1. `internal/sqlparser`: PG AST extraction, validation, schema binding, typed
   expressions and compilation. Bind source fields, JSON paths, computed values
   and aggregate outputs to distinct slots; aliases are not physical field IDs.
2. `internal/proxy/dql`: share QueryTask preparation, scheduling, metadata,
   consistency, namespace, partition selection and execution. Add a compiled
   plan preparation boundary instead of copying the old SQL task lifecycle.
3. `internal/core`: materialize typed JSON/scalar inputs and evaluate expressions
   needed before grouping. Reuse Project/Aggregation/QueryOrderBy operators and
   current segment read APIs. Preserve delayed output materialization.
4. `internal/agg` and `internal/util/queryutil`: preserve partial-state reduction
   at every distributed level, then finalize and paginate at the correct boundary.
5. HTTP adapts SQL requests and tabular output while retaining collection-level
   authorization and request controls. API/proto changes must be versioned; no
   machine-local dependency replacement is acceptable.

Function Chain supplies useful typed Arrow/map and JSON projection infrastructure.
Its search `GroupByOp` is not a relational aggregate and cannot implement SQL
GROUP BY directly. QueryView client components exist, but switching production
Proxy execution to QueryView is outside this feature.

## Execution invariants

- Q3 computes the hour BEFORE grouping; grouping by time_us and formatting the
  hour afterwards is wrong.
- Q5 merges min/max states BEFORE computing the final interval and ordering it.
- AVG merges sum/count; it does not average local averages.
- COUNT DISTINCT merges exact sets/state; it does not add local cardinalities.
- Aggregate-based top-k must not prune shard groups before global reduction.
- Two JSON paths from one physical field and min/max of one input need distinct
  result identities, even though their physical field IDs are equal.
- Typed shredding absence requests raw fallback; it is not authoritative NULL.
  Storage errors propagate instead of being converted into fallback or NULL.
- Follow current Arrow/FieldData ownership and validity contracts. SQL additions
  must not force the ordinary query path back to eager materialization.
- Keep protobuf field numbers already used on master. New plan capabilities
  need explicit mixed-version handling rather than silently ignored fields.

uses sum/count columns. `COUNT(*)` lowers to a projected non-null literal, so

### Initial implementation limits

- Ordinary Query retains its existing Arrow/delayed-materialization path.
  Plain SQL currently materializes source columns at Proxy; its typed filter
  runs before the final pagination. Without a filter/order, a native limit can
  bound the initial read. Aggregated SQL evaluates filters and expressions
  inside Project before native grouping. General SQL predicate index pushdown
  is not implemented.
- Exact DISTINCT can produce a large intermediate key set, especially with
  multiple distinct arguments. Existing output limits plus Proxy accounting
  bound returned/merged state; this implementation does not spill SQL states.
  Native `common.groupBy.maxGroups` also applies to the expanded distinct keys.
- SQL REST defaults to UTC; an explicit timezone controls temporal extraction
  and timestamp formatting. Raw JSON fallback uses batches of 1,024 rows per
  field, while typed string paths and integer casts can use the existing
  shredding reader.
- Vector SQL requires one ascending distance sort and an explicit LIMIT.
  Scalar field/literal filters use Search. JSON extraction, casts and arithmetic
  in vector filters are rejected rather than filtering an already truncated ANN
  result. L2, cosine and IP scores are converted to pgvector distance semantics.
- Casts are a supported scalar subset, not all PostgreSQL casts. Timestamp
  construction uses `to_timestamp`; numeric/internal timestamp representation
  casts are rejected. WHERE casts, joins, windows, HAVING, subqueries and set
  operations are explicitly unsupported. Duplicate output names require aliases
  because REST results are JSON objects.
- The million-row benchmark is optional. Existing `bluesky` data is reused only
  with `-bluesky-reuse` and exactly 1,000,000 rows; the harness does not fingerprint
  a reused dataset or infer sealed state from elapsed time.

## Performance continuation (2026-11-24)

P16 retains a general single-string-key path during final DISTINCT regrouping.
The original immutable string is used directly as the map key; SQL NULL has
a separate group, and the original encoded length is still charged to the
resource limit. Composite keys and exact DISTINCT sets keep their existing
behavior. No SQL text, field name or dataset-value matching is used.

Bracketed Q2 latency improved 4.30%, with 6.06% in a separate longer-warmup
confirmation. Process-wide Go allocation bytes/query fell 3.84% and allocation
count fell 20.63%. Q1 latency differences remain visible; no all-query speedup
or no-regression claim is made. P15 xxhash and P17 integer-literal batching
were measured and reverted. P17's tests passed, but Q1 latency increased in
clean controls; the rebuilt old core reproduced the historical library exactly.

All eight systems were remeasured on the same host with full responses and
independent source-oracle checks. The final matrix now includes grouped exact
DISTINCT with NULL/empty/mixed JSON keys in growing/sealed, stats off/on and
two-shard scenarios (54 checks). Relevant Go packages, SQL E2E27 and restored
native26 passed. Full repository regression, cloud and storage fault injection
remain unfinished.
