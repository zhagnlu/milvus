# 100 万行、小批量 delete：新旧模式实测

测试日期：2026-10-30。对应用户要求的 100 万行，删除 pair 数为 100、1000、1000、2000；重复的 1000 合并，另补 1024 门槛点。使用当前工作区源码重新编译并运行，未修改生产代码。

## 1. 结论

**不能只凭 100 万行判断收益，PK 列 chunk 数会改变结论。**

本次结果不支持“新模式在普遍情况下都能获益”。4 MiB 模型的 24 项配置在两次测试中均为中位耗时降低；单 chunk 的 31 轮复测中，24 项配置有 20 项退化。这些配置没有按线上请求频率加权，不能据此计算线上受益比例。适用范围与启用建议见 [主报告第 1 节](../segcore-delete-test-conclusions-20261030.zh.md)。

- 沿用此前 4 MiB 布局模型，int64 为 6 chunks、VARCHAR16 为 9 chunks。两次独立 seed 测试的 24 项配置，中位耗时均降低。100 pair 的 int64 回放收益仅约 5%～6%，部分轮次退化，不能称为稳定收益。
- 显式设为 1 chunk 时，同时间戳流式和回放的所有测试点均出现中位耗时退化。2000 pair 的 int64 回放增加约 40%，VARCHAR16 回放增加约 25%。
- **当前 1024 门槛能让 100、1000 pair 继续走二分路径，但无法拦住单 chunk 的 1024、2000 pair 退化。** 表格中的小批量新模式是强制开启后的对比，不是当前代码自动选择的路径。
- 混合时间戳流式不能直接套用同时间戳结论：单 chunk 的 int64 在 1000～2000 pair 有收益；单 chunk 的 VARCHAR16、2000 pair 两次测试方向不一致，应视为不确定。

完整历史结论与候选策略见 [主报告](../segcore-delete-test-conclusions-20261030.zh.md)。本文没有据此调整启用门槛。

## 2. 测试方法

| 项目 | 设置 |
|---|---|
| 行数 | 1,000,000 |
| PK | int64、固定 16 字节 VARCHAR；段内 PK 有序 |
| 删除输入 | 随机、无放回抽取已有 PK，输入打乱；100/1000/1024/2000 pairs |
| 布局 | 4 MiB 模型：int64 为 6 chunks，VARCHAR16 为 9 chunks；对照：两种类型均为 1 chunk |
| 流式 | `stream_same`：批内同一删除时间戳；`stream_mixed`：混合时间戳 |
| 回放 | `load`：使用混合删除时间戳；命中仍按插入时间戳筛选 |
| 首测 | seed=103001，每项 21 轮 |
| 复测 | seed=103017，每项 31 轮；所有配置统一复测，主表统一展示复测结果 |
| 环境 | Intel Core i7-8700，固定 CPU 2，GCC 11.4，`-O3 -DNDEBUG -std=c++20` |

4 MiB 模型按系统列组行宽估算并均匀切分：int64 为 24 B/行，VARCHAR16 为 36 B/行。它不是实际加载文件的 chunk 统计；1 chunk 是另一项明确指定的布局对照。

计时为**排序整理＋查找**。`old` 是当前 PR 中的二分回退路径，`new` 是强制排序后走有序查找；不是原始 master 与完整 PR 的端到端 A/B。包含时间戳复制、排序下标分配、重排和查找，不包含 IDs 解析、公共存在性过滤、真实存储 I/O、删除结构更新、tSafe 或完整进程 RSS。

沿用 [组件 benchmark](../../../internal/core/benchmark/DeleteBatchBenchmark.cpp)，从生产源码提取新模式的排序重排及查找函数。每轮交替 old/new 顺序，并轮换输入批次，不主动清空 cache。每次预热和计时调用都检查回调数量及哈希是否符合独立 oracle。

共 48 项配置，每项首测和复测各一次，得到 96 条汇总记录、11,232 组计时配对；四次 runner 调用均成功退出，未触发 oracle 校验错误。这不是完整 MVCC 或并发测试。

下表 cost 为排序整理＋查找耗时，单位为 **μs（1000 μs = 1 ms）**，取各轮中位数。耗时变化按配对加速比计算：`(1 / speedup - 1) × 100%`，**负数表示提升，正数表示退化**。它可能与两个独立耗时中位数直接相除略有差异；各轮极值见 CSV，不是置信区间。

**VARCHAR16、单 chunk、2000 pair 的混合 TS 流式结果不稳定：首测增加 8.9%，复测降低 1.3%，不能归为确定提升。** 保留两次原始记录，不用复测覆盖首测。

同 TS 时旧路径按 `(TS, PK)` 排序也会形成 PK 升序；混合 TS 时不保证 PK 升序。因此两种流式输入下，旧路径的查找访问顺序和局部性不同，不能合并为同一种性能结论。

## 6. 为什么单 chunk 也会变慢

新路径的收益来自减少逐 chunk、逐键二分的工作。只有一个 chunk 时，能省下的无关 chunk 查找很少；稀疏输入的指数探测、局部二分及分组还会增加工作。

回放另外需要新增排序。以 int64、2000 pair、单 chunk 为例：

- old：整理约 0.018 μs，查找约 302.987 μs。
- new：整理约 210.377 μs，查找约 213.996 μs。
- 查找省下约 89 μs，抵不过新增约 210 μs 的整理成本，总耗时从 303.006 μs 增至 424.613 μs。

6 chunks 下，同批量 old 查找约 496.046 μs，new 查找约 216.676 μs，节省量足以覆盖约 215.190 μs 的整理成本，整体才有收益。阶段与总耗时分别取中位数，阶段中位数之和不要求严格等于总耗时中位数。

这组测试也显示此前候选的 C≥16/32 是偏保守规则，会放弃部分 6/9 chunks 的收益；但不能为了获得这部分收益，仅降低批量门槛而重新放入单 chunk 的退化场景。还需在不同布局、批量和路径之间权衡。

矩阵目录中的分类型 CSV 与 `matrix.csv` 是同一批数据，不重复计数。源码哈希核对通过，benchmark 的结果校验未报告错误；没有执行完整 Milvus E2E、UT 套件或 RSS 测试。

在仓库根目录复现 31 轮测试：

```bash
python3 internal/core/benchmark/run_delete_size_matrix.py \
  --output-dir /tmp/delete-basic-1m-4MiB \
  --rows 1000000 --batches 100,1000,1024,2000 --cell-mib 4 \
  --types int64,varchar16 --modes stream_same,stream_mixed,load \
  --rounds 31 --seed 103017 --cpu 2

python3 internal/core/benchmark/run_delete_batch_benchmark.py \
  --output /tmp/delete-basic-1m-single-chunk.csv \
  --rows 1000000 --batches 100,1000,1024,2000 --chunks 1 \
  --types int64,varchar16 --shapes uniform_unique \
  --modes stream_same,stream_mixed,load --rounds 31 --seed 103017 --cpu 2
```

两个命令应顺序执行，避免争用 CPU。复现首测时将 rounds 改为 21、seed 改为 103001，并使用不同输出路径。
