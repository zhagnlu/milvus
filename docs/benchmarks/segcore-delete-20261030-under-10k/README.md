# Delete 每批通常不超过 1 万 pairs：范围内结论与补测

日期：2026-10-30。用户补充实际批量一般在 1 万以内，因此将常见路径的性能判断聚焦到 B≤10,000；此前几十万、百万级回放反例仍保留，但不作为这一范围的主要依据。这里 B 指实际传给本轮排序/查找的删除事件数；“一般不超过”不等同于代码已强制限制所有入口的最大批量。

后续目标已提高为至少 2 倍收益，2026-11-03 的独立补测及 C≥64 候选见 [2 倍门槛实测报告](../segcore-delete-20261103-2x-boundary/README.md)。本页保留此前“有无收益”的测试和结论，不将它们等同于满足 2 倍目标。

## 1. 当前结论

- **在这个范围内，多 chunk 场景的已测收益较明确。** 100 万行、4 MiB 模型（int64 6 chunks，VARCHAR16 9 chunks），此前 100～2000 pairs 与本次 4096/8192/10000 pairs 的测试均有中位配对加速；小幅结果仍有轮间波动。
- **单 chunk 的回放仍有退化，不需要几十万 pairs 才触发。** 本次 1 万 pairs 时，int64 回放 1.528 → 2.163 ms，配对耗时增加约 39.5%；VARCHAR16 回放 4.651 → 4.811 ms，配对耗时增加约 3.4%，后者幅度较小且轮间方向有变化。
- **单 chunk 流式随批量和 TS 分布不同而变化。** 之前 100～2000 pairs 的同 TS 流式退化；本次 4096～10000 的部分配置接近持平或改善，混合 TS 流式收益更明显。不能把单 chunk 的所有流式批量都归为退化。
- **原先为大批量回放保守设置 C≥32 的理由，需要在这个业务范围内重新评估。** 历史 1024≤B≤10000 的样本中，回放 C≥16 的 191 条记录未观察到中位数退化；这支持继续评估更低门槛，不等于已证明通用最优值，代码尚未调整。

## 2. 本次补测

使用同一组件 benchmark，从当前生产源码提取排序重排和有序查找函数，仍强制比较 old/new。old 是当前 PR 内的二分回退路径，不是原始 master 的完整实现。

| 项目 | 设置 |
|---|---|
| 数据 | 100 万行，随机、不重复的已有 PK；输入打乱 |
| 批量 | 4096、8192、10000 pairs |
| PK | int64、固定 16 字节 VARCHAR |
| 布局 | 4 MiB 行宽模型：6/9 chunks；显式单 chunk 对照 |
| 路径 | 同 TS 流式、混合 TS 流式、回放 |
| 运行 | 31 轮，seed=103031，固定 CPU 2；两项顶层命令顺序执行 |
| 机器/编译 | Intel Core i7-8700，GCC 11.4，`-O3 -DNDEBUG -std=c++20` |
| 范围 | 包含排序整理＋查找；不含完整 Milvus apply、真实存储 I/O、tSafe 和 RSS |

36 项配置，共 1116 组计时 old/new 配对。预热和每次计时均通过匹配回调数量、哈希与独立 oracle 的核对，命令成功退出；没有运行完整 UT 或 Milvus E2E。

## 3. 1 万 pairs 的具体 cost

cost 单位 **ms**，按“旧 → 新”排列，分别取 31 轮中位数。耗时变化来自配对加速比，公式为 `(1 / speedup - 1) × 100%`，因此可能与两个耗时中位数直接相除不同。负数表示配对耗时降低。

| PK | C | 路径 | cost/ms（旧 → 新） | 配对耗时变化 |
|---|---:|---|---:|---:|
| int64 | 6 | 同 TS 流式 | 3.155 → 2.203 | -31.0% |
| int64 | 6 | 混合 TS 流式 | 3.523 → 2.248 | -36.5% |
| int64 | 6 | 回放 | 2.589 → 2.203 | -13.5% |
| VARCHAR16 | 9 | 同 TS 流式 | 11.268 → 4.777 | -58.3% |
| VARCHAR16 | 9 | 混合 TS 流式 | 11.867 → 4.745 | -60.5% |
| VARCHAR16 | 9 | 回放 | 10.203 → 4.843 | -52.9% |
| int64 | 1 | 同 TS 流式 | 2.300 → 2.208 | -1.2% |
| int64 | 1 | 混合 TS 流式 | 2.728 → 2.163 | -20.4% |
| int64 | 1 | 回放 | 1.528 → 2.163 | +39.5% |
| VARCHAR16 | 1 | 同 TS 流式 | 5.277 → 4.799 | -9.0% |
| VARCHAR16 | 1 | 混合 TS 流式 | 6.318 → 4.930 | -23.0% |
| VARCHAR16 | 1 | 回放 | 4.651 → 4.811 | +3.4% |

本次 4 MiB 模型的 18 项配置均为配对中位数提升；单 chunk 的 12 项流式配对中位数提升、6 项回放配对中位数退化。**这不是每个单轮的保证，也不代表线上请求占比。**

特别需要注意：单 chunk、4096 pairs 的 int64/VARCHAR16 同 TS 流式，两个独立耗时中位数与配对比值给出的方向不同；部分单轮也跨越 1，应归为接近持平或有波动，不能强行标记稳定提升。int64、6 chunks、4096 pairs 回放配对提升仅约 4%，同样有单轮退化。单 chunk、1 万 pairs 的 int64 同 TS 流式配对提升约 1.2%，也应视为收益较弱。

所有 4096/8192/10000 数据及单轮比值极值保存在 [4 MiB 模型 CSV](main-4MiB/matrix.csv) 和 [单 chunk CSV](single-chunk.csv)。极值不是置信区间；本次这些新增点未再换 seed 复测。

## 4. 重新筛选历史小批量样本

从历史 layout、size、midpoint 三组 CSV 中，筛选 1024≤B≤10000，共 1076 条记录。包含重复配置，不是独立样本或线上请求比例；历史实际批量点并未覆盖该区间的每个整数，也没有 10000 的精确端点。此表不混入本次及之前的 100 万行补测。

| 路径 | 条件 | 记录数 | 中位数退化记录 | 最低配对中位加速比 |
|---|---|---:|---:|---:|
| 流式 | C≥8 | 508 | 2 | 0.9285× |
| 流式 | C≥12 | 372 | 0 | 1.1918× |
| 流式 | C≥16 | 336 | 0 | 1.1918× |
| 回放 | C≥8 | 283 | 2 | 0.9446× |
| 回放 | C≥12 | 212 | 0 | 1.2236× |
| 回放 | C≥16 | 191 | 0 | 1.2236× |
| 回放 | C≥32 | 123 | 0 | 1.7496× |

8 chunks 的反例出现在 4400 万行、int64、1024 pairs，输入为随机或未命中；因此即便 B≤1 万，也不能简单地“只排除 1 chunk”。C≥12/16 的结果只是已有样本表现，不是独立验证或对所有布局的承诺，尤其尚未覆盖严重不均匀 chunk、长字符串和不同硬件。

既有 50 万行、3 chunks 的 int64 回放，在历史 1024～8192 的测试点也有退化，详见 [历史加密矩阵](../segcore-delete-20261028/delete-size-midpoints-20261027/results.csv)。因此低批量并没有消除所有整理成本问题。

## 5. 对启用策略的影响

常见 B≤1 万场景可单独评估更积极的启用范围，不能继续以 150 万 pairs 的退化作为它必须采用 C≥32 的证明；但需要保留少 chunk、弱收益等配置的回退。

用户给出的是“一般不超过 1 万”，没有证明所有 `Delete` 和 `LoadDeletedRecord` 调用都满足硬上限。因此不直接修改全局规则，也不从文档中删除较大批量的反例。后续实现应按实际参与本轮处理的 B 分支，且在排序前选定路径；若 1 万仅指外部请求大小，还需核对回放等入口是否有不同批量。

```bash
python3 internal/core/benchmark/run_delete_size_matrix.py \
  --output-dir /tmp/delete-under-10k-4MiB \
  --rows 1000000 --batches 4096,8192,10000 --cell-mib 4 \
  --types int64,varchar16 --modes stream_same,stream_mixed,load \
  --rounds 31 --seed 103031 --cpu 2

python3 internal/core/benchmark/run_delete_batch_benchmark.py \
  --output /tmp/delete-under-10k-single-chunk.csv \
  --rows 1000000 --batches 4096,8192,10000 --chunks 1 \
  --types int64,varchar16 --shapes uniform_unique \
  --modes stream_same,stream_mixed,load --rounds 31 --seed 103031 --cpu 2
```
