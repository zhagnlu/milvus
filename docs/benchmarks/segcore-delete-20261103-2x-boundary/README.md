# Delete：以至少 2 倍收益为目标选择门槛

日期：2026-11-03。目标是在实际删除批量一般不超过 1 万 pairs 的范围内，找出收益余量较大的候选启用条件；不追求精确到某一个 chunk 或 pair 的最优分界。

**本轮建议的保守候选：有序 PK 列查找路径，实际 PK chunk 数 C≥64，且 1024≤实际处理的 pairs 数 B≤10000。** 这个范围在两个新 seed 的确认矩阵中，所有配置的中位加速均超过 2 倍，最弱为 **2.5868×**。这是本机、下述数据模型内的实测结论，不是所有线上请求的保证；本轮没有修改生产启用条件。

## 1. 测量口径

**2 倍定义为旧模式耗时 / 新模式耗时 ≥ 2，即新模式耗时至多为旧模式的一半。** 比较包含排序整理和查找的总耗时，不是只比较查找，也不是完整 Milvus 删除接口的耗时。

使用当前 [组件 benchmark](../../../internal/core/benchmark/run_delete_batch_benchmark.py)，从生产源码提取重排和有序查找函数，两条路径强制运行。旧模式是当前 PR 内的二分回退路径，已包含当前 PR 的重排方式，不是原始 master 的完整实现。计时包括 TS 复制、下标数组分配、排序、重排、有序检查、定位和回调计算；不含 IDs 解析、公共存在性过滤、真实存储 pin/I/O、删除结构更新、cgo 和 tSafe。

每轮交替 old/new 顺序，轮间更换输入；每次调用都核对回调数量、结果哈希和独立 oracle。CSV 的 cost 是各自耗时的中位数，`speedup` 是每轮配对 old/new 比值的中位数，两者可能不能直接相除得到完全一致的值。单轮极值不是置信区间；测试配置占比也不是线上请求概率。

## 2. 先找候选值，再换 seed 确认

探索阶段测试 16、32、64、128 个 chunk，覆盖 100 万/4400 万行、100/1024/10000 pairs、两种 PK、三种删除分布和三种处理路径，共 432 项配置。每项 7 轮，seed=110301。

下表仅筛选目标范围 1024≤B≤10000，每个 chunk 数有 72 项配置：

| PK chunk 数 C | 最低配对中位加速比 | 中位数未达到 2 倍的配置数 |
|---|---:|---:|
| 16 | 1.2076× | 23 / 72 |
| 32 | 1.6921× | 6 / 72 |
| 64 | 2.6325× | 0 / 72 |
| 128 | 4.4884× | 0 / 72 |

**16、32 个 chunk 有收益，但不能满足本轮统一的 2 倍目标。64 是这组探索点中首个全部达到目标的候选值；没有据此声称 63 不够或 64 是精确分界。**

下面用同一个具体场景展示 cost：4400 万行、int64、1024 pairs、随机不重复 PK、同 TS 流式，来自同一探索运行。单位 ms。

| C | 旧模式 | 新模式 | 配对中位加速比 |
|---|---:|---:|---:|
| 16 | 0.817 | 0.677 | 1.2076× |
| 32 | 1.148 | 0.679 | 1.6921× |
| 64 | 1.751 | 0.677 | 2.6325× |
| 128 | 2.994 | 0.666 | 4.4884× |

原始数据见 [discovery.csv](discovery.csv)。旧路径对每个 chunk、每个删除键分别二分；新路径利用有序输入推进游标并跳过 chunk 范围外的键，因此本次模型中 C 增大时，两侧成本差距扩大。

候选 64 个 chunk 的确认矩阵：

| 维度 | 设置 |
|---|---|
| 行数 | 10 万、100 万、800 万、4400 万 |
| B | 100、1000、1024、4096、8192、10000 |
| PK | int64、固定 16 字节 VARCHAR |
| 删除分布 | 随机不重复、连续区间打乱、仅 16 个候选键重复、半批候选键重复、未命中 |
| 路径 | 同 TS 流式、混合 TS 流式、回放 |
| 复测 | seed=110317、110331，各 21 轮，顶层命令顺序执行 |
| 环境 | Intel i7-8700、GCC 11.4、`-O3 -DNDEBUG -std=c++20`，固定 CPU 2 |

B=100/1000 是低批量对照，强制测试新路径，不代表当前生产代码已为这些批量启用新路径。当前生产门槛仍是 `kMinSortedDeleteBatchSize=1024`。

### 2.1 两轮确认结果

每个 seed 720 项配置，两个 seed 合计 1440 条记录、95,760 组计时 old/new 调用配对。目标范围 1024≤B≤10000 内是 **480 项不同配置 × 2 个 seed = 960 条记录**，共 35,280 组计时调用配对、20,160 个配对轮次。

| PK | 路径 | 目标范围内记录数 | 最低配对中位加速比 | 最低单轮加速比 |
|---|---|---:|---:|---:|
| int64 | 同 TS 流式 | 160 | 2.5868× | 1.5497× |
| int64 | 混合 TS 流式 | 160 | 2.7977× | 2.1428× |
| int64 | 回放 | 160 | 2.7657× | 1.3989× |
| VARCHAR16 | 同 TS 流式 | 160 | 4.3710× | 3.4997× |
| VARCHAR16 | 混合 TS 流式 | 160 | 4.4322× | 4.1700× |
| VARCHAR16 | 回放 | 160 | 4.3289× | 3.6360× |

最弱中位数来自 seed=110331、4400 万行、int64、1024 pairs、随机不重复 PK、同 TS 流式：**1.724 → 0.668 ms，配对中位加速 2.5868×**。两个 seed 都有至少 2 倍的中位数收益，不是只使用选择门槛时的探索样本。

保留全部波动：上述 960 条记录中，有 3 条出现过低于 2 倍的单轮，最低 1.3989×；没有记录到低于 1 倍的单轮。这三条分别是 seed=110317 的 10 万行随机不重复/同 TS/B8192、100 万行未命中/同 TS/B8192，以及 seed=110331 的 4400 万行未命中/回放/B1024，均为 int64。没有删除这些记录，也没有凭极值推断波动原因。

因此达成的是预先声明的“**每项配置的配对中位数 ≥2×**”标准，没有达成“所有单轮都 ≥2×”这一更强偏好。当前 CSV 只保留单轮比值的中位数、最小和最大值，没有保存每轮明细，不能由此给出精确的单轮达标概率或线上成功概率。两个 seed 仍共享同一机器和模型，也不等于跨硬件的独立验证。

包括 B=100/1000 对照后，1440 条记录的中位数也都超过 2 倍，最低 2.5292×；本轮候选仍保留原有 B≥1024 的下限。

数据：[seed=110317](confirmation-110317.csv)、[seed=110331](confirmation-110331.csv)。

### 2.2 更大 chunk 数的对照

在 C=128 上补测 100 万/4400 万行、B=1024/10000、两种 PK、五种删除分布、三种路径，共 120 项配置；seed=110331，每项 21 轮。全部配置的中位数和所有记录的单轮极值均超过 2 倍，最低中位数 **4.4137×**，最低单轮 **4.0327×**。

最弱中位数仍是 4400 万行、int64、1024 pairs、随机不重复 PK、同 TS 流式，cost 为 **2.957 → 0.675 ms**。这支持 128 这个较大测试点也有收益余量；如果希望进一步缩小启用范围，可以考虑 128，但本轮数据没有要求必须从 64 提高到 128 才能满足中位数目标。

数据：[larger-chunks-110331.csv](larger-chunks-110331.csv)。

## 4. 门槛含义、使用条件与证据边界

- **64**：本轮明确测试的候选点，并通过两个新 seed 复测；不是从“C≥64”的历史筛选结果中推定 64 这个点已经测过。
- **1024**：保留当前代码的批量下限，同时实测了这个端点；不表示 1023 必然达不到 2 倍。
- **10000**：按用户常见批量限定本轮适用范围，并实测这个端点；不表示 10001 会突然变慢。

落地时应在排序前统一决定路径，准备和查找阶段共享同一个决定。C 取查找所用同一数据视图中的实际 PK 列 chunk 数；流式 B 取存在性过滤后实际参与处理的事件数，回放 B 取本次输入事件数。不能拿外部请求大小、向量列 chunk 数或按段行数估算的 chunk 数替代。未满足候选条件的场景可以继续使用原路径，这不意味着它们一定没有收益。

- 列内 PK 唯一、全局有序，chunk 按行数均匀切分；删除输入本身覆盖重复 PK。没有把大量重复物理版本、严重不均匀 chunk、变长/长字符串的表现视为已经验证。
- 10 万～4400 万行只是已测规模；1024～10000 也只测了列出的离散点，没有穷举区间。更大 C 的收益要结合较大 C 的测试点理解，不能推广成所有布局的数学保证。
- 当前 CPU 的组件倍率不能保证换硬件、增加并发、加入真实存储 I/O 后仍达到 2 倍，也不能推导完整删除接口的倍率。
- benchmark oracle 通过不等于完整 MVCC、回调顺序、并发删除和查询可见性已验证。本轮没有运行完整 Milvus E2E 或 RSS 测试。

## 5. 复现与归档

[plan.json](plan.json) 保存探索前的判定标准、矩阵、命令及执行状态。每个 CSV 旁的 `.metadata.txt` 保存编译参数、CPU、生产源码、提取内核和 benchmark 哈希。

四次测量命令全部成功退出：探索 432 条、两次 C=64 确认各 720 条、C=128 补测 120 条，共 **1992 条记录、115,164 组计时 old/new 调用配对**。记录跨 seed/阶段有重复配置，不能视为 1992 个独立样本。每次调用的匹配 oracle 均通过。

[validation.json](validation.json) 记录完整矩阵核对、每条记录的采样数核对、CSV/元数据哈希、源码一致性及分组统计。测量前后的生产源码、提取内核和 benchmark 一致；本轮只新增测量数据并更新文档，没有修改生产代码、benchmark 或门槛。

汇总入口：[Delete 优化测试与结论](../segcore-delete-test-conclusions-20261030.zh.md)。

```bash
python3 internal/core/benchmark/run_delete_batch_benchmark.py \

  --batches 100,1000,1024,4096,8192,10000 \
  --types int64,varchar16 \
  --shapes uniform_unique,dense,repeated,repeated_half,miss \
  --modes stream_same,stream_mixed,load \
  --rounds 21 --seed 110317 --cpu 2
```
